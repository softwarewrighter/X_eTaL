Drag
Horizontal drag directly changes yaw:

Δangle = Δx * sensitivity

Rotation behavior
Automatic rotation should be deliberately slow.

Something around:

top:    -2°/second
bottom: +2°/second

Animate using the shortest path:

current angle
     ↓
 shortest angular distance
     ↓
target language
over perhaps 400–700 ms.

Then leave that half paused.

Rotation is exploration. Selection is navigation.

But homogeneous arrays matter
There is one important complication.

X_eTaL's static/homogeneous array model means this:

source = String
output = String
notes  = String
status = enum/bool
doesn't naturally form one homogeneous third axis unless everything becomes text.

I would not solve that by weakening the type system.

Instead use several aligned arrays:

sources : Idiom × Language → String
outputs : Idiom × Language → String
notes   : Idiom × Language → String
status  : Idiom × Language → Status
That's technically parallel arrays, but importantly they're not "parallel arrays pretending to be records."

They're aligned tensors sharing named dimensions.

That's a much stronger abstraction.

Think of the dataset as:

Rosetta dataset

languages     : Language
idioms        : Idiom

source        : Idiom × Language → String
output        : Idiom × Language → String
notes         : Idiom × Language → String
available     : Idiom × Language → Bool
That resembles scientific datasets much more than database rows.

What I would do for the MVP
Keep the file boring:

data.toml
But do not expose TOML's record structure to the X_eTaL application.

Have the loader normalize it immediately:

              data.toml
                  │
                  ▼
             Rust loader
                  │
          normalize/validate
                  │
        ┌─────────┴──────────┐
        ▼                    ▼
    coordinates           variables

    idioms[I]             source[I,L]
    languages[L]          output[I,L]
                          notes[I,L]
                          available[I,L]
Then hand those arrays to X_eTaL.

That means the X_eTaL implementation starts life using the same data model that future XTλN should naturally represent.

And I'd explicitly add two future milestones
M2 — Labeled/higher-rank data experiment: use the Rosetta application to investigate whether X_eTaL needs better ways to associate semantic coordinates with dimensions. Don't commit to syntax prematurely.

M3 — XTλN: design a safe, non-executable serialization format around the actual X_eTaL value model, especially type + rank + shape + nested arrays. Require round-trip tests and fuzz malformed/untrusted input.

That gives .xtln a reason to exist that is much stronger than "our project needs another configuration format." It becomes a serialization of the thing that makes X_eTaL distinctive: typed multidimensional data.
