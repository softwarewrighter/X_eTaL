6. Ambiguity and parsing risks
The biggest issues are not actually the single versus double vertical bars.

| Issue | Recommendation |
|---|---|
| | already used elsewhere | Reserve separator meaning at spatial-expression top level |
| Nested spatial expressions | Parse recursively, tracking delimiter depth |
| Operator precedence | Treat the whole construct as one primary expression |
| Binding scope | Scope lower-region variables to the entire spatial expression |
| Type checking | Resolve center operator before validating upper/lower expressions |
| Rendering | Use a mathematical layout tree, not embedded newline characters |
| Errors | Report which of the three regions is malformed |
| Macros | Allow a macro to receive the three AST subexpressions, not raw strings |

There is also a lexical issue worth checking: |~ must be recognized as a single opening token, and _| as a single closing token, rather than having either consumed by existing operators or identifier rules.

One subtlety with nested expressions: tracking parenthesis depth alone isn't sufficient. The parser must also track nested |~ ... _| constructs.

2. Three delimiter designs worth considering
Option A — Explicit sections (my preference)
|~ upper1 |~ upper2 || center || lower1 _| lower2 _|
Rules:

|~ introduces each upper expression.

|| separates the upper section from the center, and the center from the lower section.

_| separates lower expressions, with a distinct final terminator needed.

That last point is the weakness: the same symbol cannot cleanly mean both another lower expression follows and the construct is finished without additional context.

I would fix that by adding an explicit closing token:

|~ upper1 |~ upper2 || center || lower1 _| lower2 |_
Here |_ is a final closing delimiter, distinct from _|.

It works, but the ending feels unnecessarily complicated.

Option B — Symmetric region delimiters
|~ upper1 ~| upper2 || center || lower1 |~ lower2 ~|
This has visual symmetry, but it makes ~| do two jobs and introduces ambiguity unless nesting and termination are specified carefully.

I would reject this for the MVP.

Option C — Opening, separators, and closing (recommended refinement)
|~ upper1 ~ upper2 || center || lower1 ~ lower2 _|

Approach 1: Existing expression macros

Approach 2: Token-tree or raw-token macros

The macro would:

Capture the delimited input.

Split it into upper, center, and lower token sequences.

Parse each sequence as an X_eTaL expression.

Construct a generic spatial representation.

Delegate interpretation to the macro or library consuming it.

A binding.

A complete expression.

3. Consider the distinction between macros that produce syntax and macros that annotate syntax

Structural macros

Capture the nested macro invocations.

Recognize their structural roles.

6. A subtle issue: symbolic arrays need structure
There is one place where I'd retain a little caution about eliminating ASTs.

If the current macro system receives expressions as strings, it can certainly manipulate them as character arrays. But character-array operations alone don't necessarily understand:

Operator precedence.

Nested macro invocations.

Lexical scope.

Identifier binding.

Lambda parameters.

Type relationships.

For example, a macro must distinguish a comma separating two tuple elements from a comma nested inside a function argument.

So I wouldn't require a conventional tree-based AST, but I would want at least one of the following:

Balanced token sequences with delimiter nesting.

Typed symbolic-expression objects.

A structured array representation of expression components.

An array-based symbolic representation can preserve the same structural information as an AST without using traditional pointer-linked nodes.

That could become a general architectural feature of X_eTaL's macro system.

indices = grid(domains)

Macro expansion requirements
The existing macro-expansion facility should be reused wherever possible.

Viewing the original expression.

Viewing the final executable X_eTaL expression.
