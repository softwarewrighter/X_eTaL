The issues I would redirect for now
There are four things I'd put above almost all new features.

1. Fix the table / inner performance regression now
This is the clearest technical red flag I found.

The downstream measurements say the newer core made ordinary elementwise operations roughly 8× faster, which is excellent, but after higher-order operations became steppable kernels:

t_able is about 2.7× slower
i_nner about 1.5× slower
actual pages using them became roughly 1.7–2.2× slower
ML reports matrix product around 700 ns/multiply-add on the current vendored build.
Core has correctly created Saga 30 for this.

I would do Saga 30 before adding significant language features.

This isn't premature optimization anymore. table and inner product are showcase array operations, and N-body/CNN/MoE/attention naturally stress them. A newcomer should not encounter “the newer version is twice as slow.”

More importantly, establish performance regression gates:

elementwise
reduce
scan
each
table
inner
rotate
transpose
Life
small matmul
Not absolute “must be fast” thresholds initially—“must not regress >10–15% without an explicit approval” would be enough.

2. Finish the terminal
This is now tantalizingly close.

Recent core work has delivered:

steppable evaluator
       ↓
HOFs themselves steppable
       ↓
terminal grid + line editor
       ↓
worker can WAIT at []R_EAD
       ↓
user types into browser pane
       ↓
program RESUMES
       ↓
typed screen control ← current work
That removes one of the largest visible “prototype” seams.

Games still document their browser workaround as replaying the entire typed history on every input line. Once the new terminal propagates downstream, that architectural embarrassment disappears.

I'd finish this rather than interrupting it.

3. Pull macros forward again
This is where I disagree somewhat with the latest queue.

Libraries currently report macros as approximately fifth in the upstream queue, after performance, terminal and the course.

I'd prefer:

1  HOF performance regression
2  finish terminal
3  minimal Start Here / learning page
4  .xtlm macros
5  broader course
rather than finishing a substantial course before macros.

Why?

Because Extensible is in the name.

The ML README already gives an excellent three-part explanation:

Libraries extend the vocabulary.
Macros extend the language.
Native extensions extend the machine.

But the middle one is still future tense.

And three separate repos are waiting for it:

X_eTaL-libraries
    ├── Control.xtlm
    └── Test.xtlm

X_eTaL-ML
    └── network macro

X_eTaL-extensions
    └── FFI/binding macros
That's unusually strong evidence that .xtlm isn't speculative language ornamentation. Three real downstream consumers are blocked on it.

Once those three independently use the facility, the Extensible claim becomes extremely convincing.

4. Fix the small correctness/consistency bugs before publicity
Some aren't glamorous, but they're exactly what outside programmers notice.

I'd create a promotion blocker bug list containing at least:

bound Bool arithmetic inconsistency;
executable program with l: names misclassified as library;
empty Char array DISPLAY kind;
--draw argument-order CLI bug;
vendored xetal --version provenance;
extension errors pointing at facade rather than useful caller context.
None individually prevents experimentation. Collectively they say “early prototype.”

I'd rather fix those than add five more libraries.

Things I would not prioritize now
The latest plans are starting to grow again: tuples, algebraic data, local functions, complex numbers, records, additional graphics/media, more libraries, more games, etc.

They're good ideas, but I would protect the release boundary.

In particular, I would not block wider promotion on:

algebraic data types;
tuples/records;

Those become excellent post-announcement development material.

That's useful strategically: instead of showing up with a supposedly finished language and nothing to talk about next, you have months of interesting follow-up work.

Overall assessment
If I roughly scored this morning's ecosystem as ~65–70% of the way to something I'd deliberately promote outside the array-language/research circle, I'd put the current state around 80–85%.

More importantly, the remaining 15–20% is no longer “build enough stuff.”

It's:

stabilize → synchronize → explain → give people one obvious path through it.

I would actively resist adding major new feature sagas until that happens. You have enough material now that another feature is generally less valuable than making the existing feature set comprehensible, reliable, and discoverable.
