Static typing fits the core particularly well

We already reduced the semantic model toward:

Value
Function : A -> B

with apparent valence expressed through currying:

niladic: Unit -> A
monadic: A -> B
dyadic:  A -> B -> C

Make that genuinely typed:

@       : Unit

now     : Unit -> Time

neg     : Num a => a -> a

+       : Num a => a -> a -> a

shape   : Array a -> Shape

rotate  : Int -> Array a -> Array a

reduce  : (a -> a -> a) -> Array a -> a

scan    : (a -> a -> a) -> Array a -> Array a

This is already starting to look pleasantly Haskell-ish underneath an APL-ish surface language.

@ becomes much better

Our previous decision:

now @        OK
now 42       ERROR

no longer needs a special runtime check.

Simply:

now : Unit -> Time
42  : Int

Therefore:

now 42

doesn't type-check.

And:

f = now
f @

does.

That's exactly the behavior we wanted.

_l and _r can be inferred

Consider:

{ _r * _r }

Inference sees * and determines something approximately like:

Num a => a -> a

For:

{ _l - _r }

we infer:

Num a => a -> a -> a

No type declarations required.

That preserves APL terseness while giving Rust/Haskell-like compile-time checking.

Explicit annotations can exist when useful:

square : Int -> Int
square = { _r * _r }

but shouldn't normally be necessary.

HOFs become particularly nice

Reduce:

r : (a -> a -> a) -> Array a -> a

So:

+ r

can be inferred as:

Num a => Array a -> a

Thus:

sum = + r

creates a statically typed derived function.

Likewise:

+ s

scan:

Num a => Array a -> Array a

This is a major argument for static typing in this language. The type checker can tell us what all these highly compact compositions mean.

Types also help with trains

Our fork:

[f g h]

means:

{ (f _r) g (h _r) }

Types constrain it.

Suppose:

f : A -> B
h : A -> C
g : B -> C -> D

Then:

[f g h] : A -> D

That is a lovely inferred type.

And a bad train such as:

[f g h]

where:

f : A -> String
g : Int -> Int -> Int
h : A -> Int

fails at compile time.

For a language this terse, that is extremely valuable.

Types can help detect—but should not define—syntax ambiguity

I'd preserve our previous rule:

Parsing ambiguity is an error; don't ask the type checker to arbitrarily select a parse.

However, after an unambiguous syntactic parse, types can reject nonsensical compositions.

That's an important distinction:

characters
    ↓
lexer
    ↓
UNAMBIGUOUS grammar
    ↓
AST
    ↓
desugaring
    ↓
Core AST
    ↓
type/shape inference
    ↓
evaluation

Don't do C++-style parsing where knowing what an identifier means can radically alter the grammar.

Keep XeTaL's grammar clean.

Arrays introduce the interesting typing problem: shape

There are really two different questions:

Array element type?
Array shape?

Start simple:

Array<Int>
Array<Float>
Array<Bool>

with shape as runtime metadata.

So:

A : Array<Int>
shape A : Array<Int>

or preferably a distinct:

Shape

type.

Later XeTaL can explore shape typing:

Array<Int, [3,4]>

and eventually symbolic shapes:

Array<a, [m,n]>

But I would not put shape into the initial static type system.

That's exactly the sort of feature that could make the experimental language disappear into type-system research before Life works.

Broadcasting is where static typing gets interesting

For:

3 + A

you want scalar extension.

So + isn't really just:

a -> a -> a

at the surface.

There is some lifting mechanism:

Int + Int          -> Int
Int + Array<Int>   -> Array<Int>
Array<Int> + Int   -> Array<Int>
Array<Int> + Array<Int> -> Array<Int>

I would resist hardcoding those four overloads into every arithmetic function.

Instead, XeTaL should eventually formalize lifting.

Conceptually:

+ : Num a => a -> a -> a

and the array machinery lifts it.

That means the scalar function remains beautifully simple.

This also supports our everything-composes philosophy.

Extensible is arguably even more important than Experimental

Your proposed name:

eXperimental eXtensible Typed Array Language

actually describes three goals we've independently arrived at.

Experimental

You're exploring:

semantic typography;
monadic function core;
laziness;
combinators;
APL-like arrays;
trains;
static typing.

Definitely experimental.

Extensible

User-defined functions should participate identically to built-ins:

f
f^m
f_2

And ideally user-defined HOFs/combinators should be able to create the same kinds of derived functions as core operations.

That's genuine language extensibility rather than merely having libraries.

Typed

Types make terse composition safer and more explainable.

Array Language

That's the fundamental programming model.

So the name isn't forcing the architecture very much at all.

I'd borrow Hindley-Milner ideas before Rust's type system

Despite your preference for Rust, I wouldn't start by reproducing Rust typing.

For XeTaL's first type system I'd aim much closer to Haskell/ML:

static;
strong;
inferred;
parametric polymorphism;
first-class functions;
algebraic types eventually;
type classes/traits later.

You want:

square = { _r * _r }

not:

square: fn<T: Numeric>(x: T) -> T = ...

The compiler should infer approximately:

square : Num a => a -> a

The source remains APL-terse.

Rust is an excellent implementation language, but ML/Haskell is probably the better conceptual model for XeTaL's initial type inference.

I'd start with:

Array<T>
Function<A,B>

plus type variables:

Then the core library can express:

Already enough to make the language extremely interesting.

Then test combinators through their types

This could become one of XeTaL's showcase features.

The compiler infers:

I : a -> a

K : a -> b -> a

B : (b -> c) -> (a -> b) -> a -> c

C : (a -> b -> c) -> b -> a -> c

W : (a -> a -> b) -> a -> b

Those inferred signatures are almost proofs that your combinator implementation is structurally correct.

And your browser UI can show them on hover.

Hover:

[f g h]

and see:

A -> D

where
  f : A -> B
  g : B -> C -> D
  h : A -> C

For a compact language, that's enormously useful.

Life gets more interesting too

Our target:

life = { (+ r -1 0 1 t_12 _r) = 3 + _r }

could infer something approximately like:

life : Array<Bool> -> Array<Bool>

perhaps with numeric coercion/lifting around booleans needing a deliberate design decision.

I'd actually use the type checker to make us confront that: should Bool implicitly become 0/1?

APL says effectively yes.

A strongly typed language might say no.

We could instead define a boolean numeric representation or a constrained lifting rule.

That's exactly the kind of decision the tests should force us to make rather than accidentally inheriting from APL.

XeTaL — eXperimental eXtensible Typed Array Language is therefore a substantially better description of what we're designing than HoFaL was.
