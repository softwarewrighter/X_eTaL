Reported by X_eTaL-games (their docs/xetal-asks.md row 29, 2026-10-11): a comparison's result inside a tuple stops being usable as a number once bound at the top level: with u:n_um := { (a, m) -> 0 + m } and u:n_ew := { z -> (z, 0 < 1 2 3) }, 's := u:n_ew 5' then 'u:n_um s' is type-mismatch 'expected a number, found Bool', while 'u:n_um (5, 0 < 1 2 3)' gives 1 1 1. Not library-specific (one file fails the same way). Cause: closing a top-level value (xetal-types closing.rs) keeps a bare condition a condition (T1) but defaults a condition nested in a compound type (a tuple part) to Bool at the binding. Fix within T1: a condition stays a condition wherever it sits in the value's type (tuple parts, boxes), so a later use decides; test-first (spec cases: the reported pair, a nested tuple, a boxed one, and that a guard on such a part still works), golden for the library case; record in the register; add the ask to docs/asks.toml (games) as landed; tell the games agent through the ledger.
